# ⭐ S3 Object Lock + Legal Hold
(compilance -WORM storage)

means s3 object lock allows to sotre object in WORM(write once ready man)  MODEL,means once written object cannot be deleted or modified for a defined period.
purpose is to  compilance,financial record.creititcal data,audit logs and so

🚀 Modes of object lock

1 Governance Mode:
  object can't be deleted by most users but priviledged users (with special IAM permission ) can remove it
  used when compilance s reuqired but company admin still need override capability
  example iam permission needed to override:
    ``` s3:BypassGovernanceRetention ```

2. Compliance Mode
Object cannot be deleted or modified by ANYONE, not even AWS root user
The strongest protection
Used for legal compliance (SEC Rule 17a-4(f), etc.)
Exam Trick ❗
➡️ Compliance mode cannot be disabled early
➡️ Even root cannot bypass it
➡️ No one can reduce retention period once set

⭐ Object Retention Periods
You define:
Retention Until Date or Retention for X days/years


# ⭐ Legal Hold

Separate from Object Lock.
Legal Hold:Blocks deletion,No expiration,Can be ON or OFF anytime,Meant for lawsuits, investigations,Does NOT require compliance mode

Exam difference:
Feature	Object Lock Retention	Legal Hold
Fixed time?	✔ Yes	❌ No
Changeable?	❌ (Compliance) / ✔ (Governance)	✔ Anytime
Purpose	Compliance	Temporary investigation
Prevents deletion?	✔ Yes	✔ Yes

### Note:You cannot enable Object Lock on an existing bucket unless you used special API or CLI at creation.

⭐ CLI Example (Exam loves these)
Put an object with governance mode:
```
aws s3api put-object \
  --bucket my-bucket-lock-test-animesh \
  --key record.csv \
  --object-lock-mode GOVERNANCE \
  --object-lock-retain-until-date "2025-12-31T00:00:00Z"
```
Put legal hold:
```
aws s3api put-object-legal-hold \
  --bucket my-bucket-lock-test-animesh \
  --key record.csv \
  --legal-hold Status=ON
```

⭐ 2️⃣ What is NOT Replicated (Exam Critical)
Memorize this list — exam GUARANTEED.

❌ Delete markers	No by default	Must enable “Replicate delete markers”
❌ Bucket-level settings	No	Only objects replicate
❌ Versioning status	No	You must enable it manually
❌ Lifecycle policies	No	You must recreate them

⭐ SSE-KMS Replication 
S3 can replicate KMS-encrypted objects ONLY IF:
✔ KMS key on source allows:
```
kms:Decrypt
kms:DescribeKey
kms:GenerateDataKey
```
✔ KMS key on destination allows:
```
kms:Encrypt
kms:GenerateDataKey
```
❓Exam question:
“Replication of SSE-KMS objects failed. Why?”
Answer:
➡️ Missing KMS permissions on either source or target key.

⭐ Cross-Account Replication Requirements
When source and destination buckets are in different AWS accounts, you must:
Enable versioning on BOTH
Create replication role
Allow destination bucket to accept writes from source role
Grant read permissions on source
Add bucket policy on destination

Exam likes:
❓“Why CRR to another account failed?”
✔ Destination bucket must allow s3:ReplicateObject
✔ Source bucket must allow s3:GetObjectVersion


⭐ Replication Time Control (RTC)
This is an optional feature:
Guarantees 99.99% replication within 15 minutes
Paid service
Good for compliance/financial data
Exam question:
“How to guarantee replica object availability within predictable time?”
Answer:
➡️ Use S3 RTC (Replication Time Control).

⭐ Replication Filters
You can replicate only:
Specific prefixes
Specific file types (*.csv)
Specific tags

Exam scenario:
“Only files in the /raw prefix should replicate.”
Answer: ✔ Use prefix filter = raw/


⭐ 9️⃣ Bi-Directional Replication?
(This is EXAM GOLD)

AWS S3 does NOT support automatic cyclic or bi-directional replication.
Meaning:
Source → Destination
Destination → Source
This requires two separate rules.
Exam question:
“How to maintain fully synchronized buckets across regions?”
✔ Create two CRR rules, one in each direction.

# ⭐ S3 performance optimization

So, S3 is massively scalable by defualt but design and access way determines real-world performance
so Performance issue arrises on client side design not S3 itself.

**Object key naming**
previosuly it was recommended to not use sequential prefixes like /2025/01/01/
but s3 no longer has prefix based limits
📌 Recommendation: logical predictable structure(for client side) and avoid extremely deep nesting
if somehow exceed 3500+ puts/sec on one prefix then need to redisgn keys


**upload performance optimization**

-> using Multipart upload :
basically when file size is big enough ,then it should be go with multipart upload like above 100 MB or 1 GB

it make benefit like parallel upload,faster retries ,better throughput and fault tolerance

**parallel uploads**
uploading muliple file concurrently, SDKS(boto3,aws cli) supports this natively

CLI EXAMPLE
```
aws s3 cp largefile s3://bucket/key --expected-size 500000000
```

**tcp and netwrok tuning**
increases socket buffers,max connections,avoid single threaded uploads

**download(GET) performance optimization**

A. RANGE GETs
split download into byte ranges and downlaod in parallel

B.  cloudfront in front of s3
it reduces latency ,offoad get traffic,chaches hot object
⭐ best for read heavt workload

**Storage class perofmance differences matters**
never use glacier classes for hot data

when global users,long distance uploads,interent based clients .

when readhaeavy workload ,static or frequently accessed data,lower latency needed

**small files problem**
millions of small objects,high request cost,poor query performance
so sol is convert to parquet/orc ,batch or compact files,,partition data
so in short use columnar format and partitioning when athena queries are slow and expensive


**S3 Request Costs (important for performance + pricing)**
Expensive operations:
LIST,GET
Cheap:
PUT,HEAD
Optimization tips:
Use S3 Inventory instead of LIST for large buckets
Use S3 Select for filtering instead of downloading large files


**S3 Byte-Range Fetch (Exam)**
S3 supports fetching partial content:

Range: bytes=0-1000
Useful for:
Resuming downloads
Only reading header of large files
Parallelizing downloads by splitting file into ranges
