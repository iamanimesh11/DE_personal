Q1 — Deduplicate GPS Events: Same Truck, Same Emission Time
------------------------------------------------------------

The GPS device sometimes emits the same ping twice due to network
retry logic. Two events are considered duplicates if they share the
same truck_id AND emitted_at — regardless of how different their
ingested_at timestamps are.

Deduplicate gps_events keeping the earliest ingested_at record
for each (truck_id, emitted_at) pair. Return one clean row per ping.

Expected output — 7 rows (3 duplicates removed):

Q5 — Truck Idle Detection: Speed = 0 for More Than 5 Minutes
-------------------------------------------------------------

A truck is considered "idling" if its speed_kmh = 0 for two or
more consecutive GPS pings (emitted 30 seconds apart each) — meaning

Using the deduplicated GPS events from Q1, find all trucks that
were idling and how long they were idle (first idle ping to last

 Extend data with more speed=0 pings to test multi-ping idle logic.)

Q6 — Multi-Source Reconciliation: GPS vs Delivery Events
---------------------------------------------------------

SH01 was delivered to C01 at 14:00 on Mar 01 (from delivery_events).
T01 was the truck on route R01 (from trucks table).

Cross-check: at 14:00, where was T01 according to GPS?
If T01's last known GPS ping before 14:00 is more than 30 minutes
old, flag it as 'gps_gap' — the truck went dark before delivery
confirmation, which is suspicious.

Write a query that for each delivered shipment finds:
- delivery confirmed_at time
- the truck assigned to that route
- last GPS ping time before delivery
- gap in minutes between last GPS ping and delivery
- flag as 'gps_gap' if gap > 30 minutes, else 'ok'

Expected output:

|-------------|-------------|---------------------|----------|---------------------|-------------|----------|
| SH01        | C01         | 2024-03-01 14:00:00 | T01      | 2024-03-01 08:01:00 | 359         | gps_gap  |

Q7 — Data Quality Gate: Validate GPS Events Before Loading
-----------------------------------------------------------

Before loading gps_events into the clean GPS table, run a
quality gate that checks ALL of the following in one query:

1. NULL truck_id
2. speed_kmh < 0 or speed_kmh > 200 (physically impossible)
3. emitted_at > ingested_at (event claims to be from the future
   relative to when it was received — clock skew or corrupt data)
4. lat outside India bounds (lat < 8.0 or lat > 37.0)
5. lng outside India bounds (lng < 68.0 or lng > 97.0)
6. Duplicate (truck_id, emitted_at) combinations

Return one row per failed check with check name and failed row count.
Pipeline should halt if any check returns failed_rows > 0.

Expected output (with sample data):
| check_name              | failed_rows |
|-------------------------|-------------|
| duplicate_gps_events    | 3           |

Q9 — Pipeline Audit: Detect Missing Pipeline Runs
--------------------------------------------------

Your pipelines should run every day. Using pipeline_watermarks
and the date range 2024-03-01 to 2024-03-03, detect which
pipelines missed a run on which dates.

A "missed run" means no watermark update occurred for that pipeline
on that calendar date — i.e., the watermark did not advance past
midnight of that date.

Also compute: how many days has each pipeline been behind
(days since last successful watermark update).
